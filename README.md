# sing-anytls

AnyTLS 客户端和服务端协议库。TLS 握手、证书、监听、目标拨号和 UoT 转发由调用方实现。

## 可选的服务端流量整形

在 `ServiceOptions` 中设置 `TrafficShaping` 即可启用，单用户和多用户服务都支持：

```go
service, err := anytls.NewService(password, anytls.ServiceOptions{
    Handler: handler,
    TrafficShaping: &anytls.TrafficShapingOptions{},
})
```

`TrafficShaping: nil` 保留原有发送行为和默认填充策略。配置会被复制，创建服务后修改传入结构不会影响已有服务。此功能不需要客户端新增配置或协商扩展，也不改变认证、命令字、帧格式和流语义。

启用后：

- **下行分包及填充**：仅在完整帧边界追加标准 `cmdWaste`。大响应最多拆成一次主体写入和一次有界的填充尾段，避免连续发送大量小片段，也不会仅因分片就耗尽整形窗口。
- **覆盖复用流**：每次接受新流，随机重开数据整形窗口；不增加会话总填充预算。SYNACK、FIN、心跳等控制回复在数据窗口结束后仍可填充，但共用同一预算。
- **合并已经就绪的控制回复**：填充策略更新和服务端版本设置一起进入发送路径，减少两次独立短写入。不会等待后续应用数据，也不会延迟 SYNACK 或服务端主动发出的欢迎消息。
- **可变长度上传策略**：未显式设置 `PaddingScheme` 时，服务创建时生成一次标准策略，认证填充使用 `64-512` 范围。后续规则使用配置的长度范围，并在仍有数据时使用 `4096-8192`、`64-256` 的附加目标，减少常见握手超过单个目标后原样发送剩余数据的问题。仍是原有语法，无法保证任意大上传写入均被填充。策略在服务生命周期内稳定，不会每次连接都重新生成。

显式提供 `PaddingScheme` 会覆盖自动生成的上传策略，`UpdatePaddingScheme` 仍然有效；两者不改变独立的下行预算。要只启用下行增强而保持原上传策略，可以传入 `PaddingScheme: anytls.DefaultPaddingScheme`。

### 参数与开销

所有字段为零时使用默认值：

| 字段 | 默认 | 范围及含义 |
| --- | --- | --- |
| `MinRecordSize` | 256 | 最小连接写入目标长度，至少 7 字节 |
| `MaxRecordSize` | 1400 | 最大目标长度，不超过 16384 字节 |
| `MinRecords` | 8 | 每个数据窗口至少覆盖的逻辑写入次数；分片和控制回复不重复扣次数 |
| `MaxRecords` | 16 | 最大次数，不超过 256；会话创建或接受新流时重新抽样 |
| `MaxPaddingBytes` | 16384 | 每会话最多添加的下行字节，包含 WASTE 帧头；允许 7 至 1048576 |

最小值不得超过最大值。默认参数只是有界的实验起点，不是通过真实流量训练的浏览器特征模型。

窗口结束后普通数据直写，新流可重新开启窗口；控制回复无需消耗数据窗口。预算不足以达到目标长度时跳过本次填充，不把剩余预算强制凑成固定长度尾包。全局预算耗尽后所有流都停止增加填充，也不再为整形而分片。不会发送独立定时掩护流量，也不添加随机 sleep。

`MaxPaddingBytes` 只约束下行，不约束客户端上传填充和 TLS/TCP/IP 开销。自动生成的上传策略最多涉及 16 个逻辑写入（默认范围内），大目标会带来额外上传流量；应分别测量上下行。需要自行控制上传成本时，显式设置 `PaddingScheme`。

这里的 record 指向提供的 `net.Conn` 写入的数据，包含 AnyTLS 帧头。它不是 IP 包、MTU 或 TLS record 的保证；TLS 实现和 TCP 分段会再次改变实际包形态。大数据的主体写入不受目标长度限制，尾段才使用有界长度。

### 认证与回落

服务端按字节流读满 32 字节认证摘要，支持认证和填充跨多个 TLS record/TCP read；单用户摘要采用常量时间比较，不根据秘密前缀提前回落。

`ServiceOptions.HandshakeTimeout` 限制摘要、填充长度和填充内容的读取总时间，零值默认 10 秒，负值报错。握手期间响应 context 取消，成功后及进入回落前清理临时读期限。超时/EOF 前已经读取的未认证字节会原样交给 `FallbackHandler`；错误用户表更新不会覆盖当前用户表。

不足 32 字节时，如果已收到一整行至少 3 个字符的可打印文本（如 `hello\r\n`、`GET / HTTP/1.0\r\n\r\n`），立即进入回落，和普通 Web 服务器一样马上响应；判断只看字节形态，不比较密码。其余不足 32 字节且未关闭写端的数据（二进制、没有换行的半行）仍等到期限才进入回落。并非主动探测免疫。真实 HTTP/TLS 前端的短请求响应、证书、ALPN 和超时策略仍需部署层验证。

### 能力边界

- 已有客户端的**首次认证**仍使用自己的初始策略；服务端下发策略只能影响客户端接收后的行为，其缓存和生效时机由客户端决定。
- 此库不能改变客户端的 TLS ClientHello，也不负责 TLS ServerHello、证书、ALPN 或外部监听层的行为。
- 长度变化不等于隐藏方向、时序、嵌套 TLS 握手及长连接行为；填充本身也可能形成可分类特征。本功能没有经过真实 DPI 分类器评估，不能声称不可识别或等同于普通 HTTPS。
- 未认证连接仍走原有 `FallbackHandler`。填充不会把服务端变成 HTTP 网站，也不会自动解决主动探测。
- 仅使用标准帧以维持协议兼容，但无法保证所有闭源客户端没有实现差异；发布前仍需用实际使用的客户端版本回归。

## 验证

```sh
make test
go vet ./...
(cd test && go vet ./...)
(cd test/mihomo && go vet ./...)
(cd test && go test -run TestTLSRecordTraceAcrossReusedStreams -v)
go test -run '^$' -bench BenchmarkDownlinkShaping -benchmem
```

根模块测试验证帧边界、数据完整性、填充预算、复用窗口、配置校验、v1/v2 控制帧、短写入、阻塞写入关闭、认证分片/超时/取消和回落字节完整性。独立 `test` 模块验证旧客户端互操作、多用户、复用、大数据及并发传输、服务端主动发数据、回落，以及带证书校验的 TLS 1.2/1.3。`test/mihomo` 使用 Mihomo v1.19.32 的真实会话客户端做相同 TLS 版本的互操作，具体范围见其 README。

`test/go.mod` 固定参考客户端 `github.com/anytls/sing-anytls v0.0.11`。本次修改也用临时 modfile 将它替换为 v0.0.13，运行全部测试和 race 检查；没有修改仓库的依赖锁定。

微基准每次模拟一个新会话：2 次短控制帧写入加 4 次应用数据写入。Apple M4 上一次 200ms 采样结果如下（不同运行会有波动）：

| 单次应用数据 | 模式 | 平均额外字节/会话 | 平均写入次数/会话 | CPU 时间/会话 |
| --- | --- | --- | --- | --- |
| 1 KiB | 原发送方式 | 0 | 6 | 约 12 ns |
| 1 KiB | 默认整形 | 2395 | 6 | 约 1.89 µs |
| 32 KiB | 原发送方式 | 0 | 6 | 约 13 ns |
| 32 KiB | 默认整形 | 3311 | 10 | 约 3.61 µs |

基准使用计数连接，**不包含真实网络或 TLS 成本**，也不是吞吐量或抗识别测试。短连接带宽开销较明显，部署时应结合实际抓包调整预算，比较连接延迟、带宽、包长/方向/时间序列与分类误报率。

TLS 1.3 实际加密记录测试中，原路径的 7 字节 FIN 产生 24 字节 record payload；一次增强采样中两条复用流的 FIN 分别产生 1049、712 字节 payload。大数据后的尾段和第二条流也经过填充。该测试证明具体长度变化和复用覆盖，不证明整体流量不可分类。

公开来源与限制见 [协议弱点检查](docs/weakness-review.md)，部署验证步骤见 [后续工作](docs/follow-up.md)。
