# 后续工作

当前代码已完成服务端有界整形、复用流覆盖、控制回复填充和认证读取加固。现阶段不继续增加发送延迟、空闲掩护流量或修改协议；下面的工作需要真实运行环境和客户端。

## 1. 在服务端调用方启用

此仓库是协议库，没有独立服务器入口。调用方创建 `NewService` / `NewMultiService` 时设置：

```go
anytls.ServiceOptions{
    Handler:          handler,
    TrafficShaping:   &anytls.TrafficShapingOptions{},
    HandshakeTimeout: 10 * time.Second,
}
```

对照实例使用 `TrafficShaping: nil`；其他 TLS、证书、监听、目标转发参数保持相同。V2bX 当前使用另一模块路径及 API，后续需要单独适配 sing-box 服务端，直接给旧模块加 replace 不足以接入。无需要求现有客户端增加新字段。

服务端必须正确处理 TLS 和证书校验。需要普通网站回落时，由调用方提供真实 `FallbackHandler`，并验证协商的 ALPN 与实际服务一致。不要仅为改变特征随意声明不支持的 HTTP 协议。

## 2. 跑真实客户端矩阵

先记录每个客户端的名称、版本、系统和核心版本。已自动验证参考客户端 v0.0.11/v0.0.13，以及 Mihomo v1.19.32 的会话实现；尚未覆盖完整 Mihomo 应用配置及闭源客户端。

对实际使用的客户端逐项验证：

- 冷启动首次连接、收到新策略后的再次连接、空闲会话复用。
- 网页、下载、服务端先发消息；至少一次大响应后继续小请求。
- 多连接并发、断网重连、取消请求、服务端关闭连接。
- 通过调用方的 UoT 适配验证 DNS 和 UDP；本库的会话测试不等于完整 UDP 应用测试。
- 错误密码、普通 HTTP 请求、分片认证、短于 32 字节的探测、慢速不完整请求。

重点观察短探测的回落延迟：读满认证摘要前不能知道对方是否为合法分片，默认可能等待 10 秒。这个取舍需要与真实前端行为一起评估。

## 3. 做配对抓包和成本测量

同一网络、同一客户端、同一业务负载下，分别抓取原版、增强版以及真实 HTTPS 基线。区分首次连接、复用连接、短网页请求和大文件流，不要把负载差异当成协议差异。

同时记录：TLS record 长度、上下行方向、时间间隔、TCP 分段/重传、首字节延迟、吞吐、CPU 和上下行额外流量。用 `test/traffic_trace_test.go` 的记录测试作本地回归，但它不是实网抓包的替代。

调参顺序：先测默认值；上传开销过高时显式设置经过测量的 `PaddingScheme`；下行开销过高时减少 `MaxPaddingBytes`，然后再调整长度范围与窗口次数。预算是整条会话共享的，不能期待耗尽后的长期连接仍保持相同覆盖。

没有目标流量样本时不要宣称某组随机范围“像浏览器”。如需要证明识别率下降，应在独立采样的测试集上比较分类召回率和误报率，而不仅比较单包长度；训练/测试连接不能互相泄漏。
