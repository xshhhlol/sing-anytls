# AnyTLS 服务端特征检查

检查日期：2026-10-21。范围是保持现有 AnyTLS 客户端兼容，仅调整服务端协议库；不包含面板、外层 TLS 终止器和客户端修改。

这里区分三种证据：协议明文规定、可复核的实现行为、通用流量分析研究。论文中的代理分类结果不能直接当成当前 AnyTLS 版本的识别率。尚无本项目对真实 DPI 分类器的评测数据，也没有据此承诺“无法识别”。

## 已核实的依据

1. [官方 FAQ 的已知弱点](https://github.com/anytls/anytls-go/blob/main/docs/faq.md#已知弱点)列出：下行未整形、初期紧邻发送多个包、填充语法有限、嵌套 TLS 往返和长度开销、主动探测风险。作者明确表示默认策略仅为示例，并不保证其抗识别性。这些是设计边界，不是已部署检测规则的证明。
2. [协议规范](https://github.com/anytls/anytls-go/blob/main/docs/protocol.md)允许双向 `cmdWaste`，收端必须读完并丢弃。服务端通过既有 `cmdUpdatePaddingScheme` 更新策略；版本 2 客户端还依赖设置回复、SYNACK 和心跳语义。因此兼容增强应保持帧结构、命令、顺序和及时响应要求。
3. [USENIX Security 2024 论文](https://www.usenix.org/conference/usenixsecurity24/presentation/xue-fingerprinting)证明，一些代理的嵌套 TLS 握手可通过加密后的方向、长度和时序分类；随机填充及复用有局限，尤其不能消除握手往返和突发总量。研究早于 AnyTLS 发布，不能据此断言它测试过 AnyTLS。
4. [Mihomo 会话实现](https://github.com/MetaCubeX/mihomo/blob/Meta/transport/anytls/session/session.go)具有丢弃 `cmdWaste`、处理策略更新和读取完整帧的路径，为采用标准帧的兼容性提供源码依据。它不能替代指定发行版本的互操作测试，也不能代表闭源客户端。
5. [官方 issue #46](https://github.com/anytls/anytls-go/issues/46)中作者确认，参考实现让现有会话也采用新策略。因此准确的边界是“无法改变已经发送的数据；收到策略后的生效时机取决于客户端实现”，而非一概认为只能影响下一条连接。
6. [NaïveProxy 的架构说明](https://github.com/klzgrad/naiveproxy/blob/master/README.md#architecture)使用实际 HTTP 前端及应用层路由处理探测。这说明完整应用行为的重要性；它不是单纯给 AnyTLS 加填充或声明 `h2` 即可实现的效果。

## 威胁、兼容措施与剩余边界

下表是检查和实现选择的依据，不表示每一项已经实现或经实网验证。

| 可观察特征或问题 | 服务端可采取的兼容措施 | 剩余边界与验证重点 |
| --- | --- | --- |
| 设置、SYNACK、FIN 等短回复的固定长度 | 在完整帧边界追加标准 WASTE；合并已经就绪的控制回复 | 填充不得插入帧体；不能为了等待应用数据而卡住服务端先发流或 SYNACK |
| 一个大响应迅速用完初期分包次数，后续握手不再处理 | 区分应用写入、分片次数和字节预算；验证多阶段小响应是否仍被覆盖 | 扩大范围会增加写调用和带宽开销，不能仅靠增加随机数证明效果 |
| 每条复用流的新握手在会话初期窗口之外 | 评估有界的重新覆盖或概率填充，严格保留会话总预算 | 新流数量不应变成无限填充放大器；应测试并发流和长连接成本 |
| 多个小写入紧邻形成突发 | 可选的短窗口合并或发送调度，设置明确的延迟和内存上限 | 纯分片可能增加包数量；增加等待也可能产生新指纹，需对照抓包 |
| 认证固定模板、客户端初始突发 | 用原有语法下发可变策略，避免每会话反复换策略 | 首次 TLS ClientHello、已经发出的认证以及客户端发送时机不能被服务端追溯修改 |
| 非认证请求出现特有关闭、截断或长时间等待 | 保留探测字节交给真实回落服务，覆盖短请求、分片、错误输入与 EOF | TCP/TLS 的 Read 边界不是协议边界；简单“读满 32 字节”会让短 HTTP/2 前言等请求等待 |
| 慢速或不完整的认证长期占用资源 | 可配置认证期限与有界缓冲，在认证完成后撤销临时期限 | 太短会误伤高延迟或分片客户端；固定关闭期限也可能成为特征，不能称为探测免疫 |
| TLS 握手、证书、ALPN 与应用行为不一致 | 在调用方配置真实 TLS 和回落服务，确保协商内容能被实际处理 | 本库接收已有连接，无法单独改变 TLS 栈；网站回落不会把认证后的流量变为 HTTP |
| 嵌套 TLS 的方向、往返与长连接统计 | 同时测量长度、方向、时间和复用行为，避免只看单包长度 | 保留现有客户端和端到端加密时无法完全消除；随机分布也不等于浏览器流量分布 |

## 优先级与验收

优先处理确定的正确性问题：认证分片、回落字节完整性、帧边界、超时清理、关闭唤醒及资源上限。随后改进有界整形的覆盖范围，最后才评估需要增加延迟或空闲掩护流量的实验策略。没有测量依据时，不默认开启持续填充，也不把另一组固定模板称为“去特征”。

兼容验收至少覆盖参考客户端、Mihomo、TLS 1.2/1.3、首次连接与更新策略后的连接、复用流、服务端先发、大响应后的小响应、异常关闭和限额耗尽。对闭源客户端，应记录具体应用及版本后人工验证。

流量评估应在相同网络与业务负载下比较原版、增强版和普通 HTTPS，分别记录 TLS record、TCP 分段及重传，不能把一次 `net.Conn.Write` 当成一个 IP 包。指标包括首字节延迟、吞吐、额外字节、写入次数，以及独立测试集上的分类召回率和误报率。单次连通、race 检查或包长变化只证明相应工程属性，不证明抗识别效果。
